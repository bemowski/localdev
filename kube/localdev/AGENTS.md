# AGENTS.md: working with localdev

Instructions for AI coding agents (any tool) that integrate an application with localdev or use a
localdev cluster. Humans: the same rules apply, see [readme.md](readme.md).

## What localdev is

A local Kubernetes cluster (k3d, k3s inside Docker) that replaces docker compose for app development.
It is driven by `mise` tasks run from this folder. A **profile** picks which **components** run; each
component is a folder of manifests (plus an optional image build) that k3s applies automatically.
SSO, observability (Grafana, Prometheus, Loki, Tempo), an image registry and a secret store are always on.

## The rule: integrate through a component, don't modify localdev core

localdev is shared by many developers and projects. An app plugs in as a **component**, preferably
an **external** one that lives in the app's own repository (`<project>/localdev/`) and is registered
in the developer's `local.toml`. Make a real effort to solve every integration need from inside the
component. **Do not edit localdev's core to make one app work.**

**Core (do not modify):**
- `.mise.toml`, `profile.py`, `hostfacts.py`, `k3d.yaml`
- `manifests/` (platform, infra, apps layers), `grafana/`, `registry/`
- the built-in components: `components/{cnav,docs,external-secrets,postgres,nats,keycloak,knative}/`
- `secrets.defaults.toml`, and `profiles.toml`. Adding a *shared* in-repo component there is a
  maintainer decision; propose it, don't just do it.

**Yours to edit:**
- your component folder: `manifests/`, `build.sh` or `docker/`, `dashboards/`, and its own
  `secrets.defaults.toml`
- `local.toml` (gitignored, per developer): registers external components and personal profiles
- `secrets.store.toml` (gitignored): the developer's own secret values. Change it only when asked.

**Every common need already has an extension point:**

| need | how, from inside the component |
|---|---|
| deploy something | a YAML file in `manifests/` named `<layer number>-<n>-<name>.yaml` |
| build an image | `build.sh` (any build tool; push `$IMAGE`) or a `docker/` folder with a Dockerfile |
| a URL on `http://localhost/<name>/` | an Ingress with the `sso` Middleware (copy the guide's example) |
| deploy after Postgres/NATS, in the right layer | `requires = [...]` and `layer = "..."` in `local.toml` |
| a row in cnav's status column | label workloads `localdev/component: <name>` |
| secrets | an ExternalSecret against ClusterSecretStore `localdev`, dev values in your `secrets.defaults.toml` |
| a login shown in cnav's Credentials tab | a store entry with a `password` key (automatic) |
| roll pods when a secret changes | annotation `reloader.stakater.com/auto: "true"` |
| a database / one-time setup | an idempotent init container (see the guide) |
| a Grafana datasource or dashboards | a Secret labelled `grafana_datasource: "1"` in `monitoring`; `dashboards/*.json` |
| show up in cnav's Events | normal Kubernetes Events (anything that emits them, or create one) |

**If something really can't be done from a component** (e.g. a new host port, which lives in
`k3d.yaml`), stop and tell the human what's missing, why the component can't cover it, and the
smallest core change that would. Don't patch core quietly. Don't work around it either: no
`kubectl apply` of objects that belong in a manifest, no edits under `runtime.profile/`, no manual
changes inside the cluster that a recreate would lose.

## Never touch

- `runtime.profile/`: generated by `profile.py` and mounted into the cluster. Never edit or delete it.
- `runtime.data/`: persistent data (Postgres, registry, telemetry). Only `mise run cluster:clean` removes it.
- `.kubeconfig`, `secrets.store.toml.asc` (encrypted; the human re-encrypts and commits it), and any
  archives or files the developer keeps here that you didn't create.

## Working loop

Run from `kube/localdev/`. For `kubectl`, use the cluster's kubeconfig:
`KUBECONFIG=$PWD/.kubeconfig kubectl ...`.

```bash
python3 profile.py check           # validate profiles.toml + local.toml (components, paths, layers)
mise run cluster:profile           # list profiles; mise run cluster:profile <name> switches (adds/removes)
mise run build <component>         # build + push the component's image, restart its pods
mise run secrets:sync              # push secrets.store.toml / secrets.defaults.toml into the store
mise run secrets:list              # entries and keys (never values)
mise run cluster:status            # nodes, Helm jobs, ingresses
```

Done means:
- the pods are Ready;
- `http://localhost/<name>/` answers, with SSO in front;
- the component's cnav status row is green;
- logs show in Grafana (Explore → Loki, `{namespace="<ns>"}`).

Saved manifests apply on their own within seconds, as long as the component is inside the mounted
workspace. Otherwise, re-run `mise run cluster:profile`.

## Safety

- **Ask first** before anything destructive or disruptive:
  - `cluster:destroy` and `cluster:recreate`;
  - `cluster:clean`, which deletes `runtime.data`;
  - a profile switch that removes components the developer may be using;
  - deleting namespaces or PVCs.
- **Never print, log or commit secret values.** To check one, compare hashes. `secrets.store.toml`
  is gitignored, and only its encrypted `.asc` is committed, by the human.
- **Don't commit or push unless asked.**

## Manifest gotchas

The full list is in the [manifest rules](docs/content/cluster-layout.md#manifest-rules).
- **File names are unique across the whole cluster:** `<layer number>-<n>-<name>.yaml`, dashes and no
  dots. k3s tracks each file by its base name.
- **YAML only.** k3s also applies every `.json` it finds, so don't put JSON in `manifests/`.
- **Each file creates the namespaces it uses.** k3s retries a file until all of it applies.
- **Removing an object from a file deletes it; deleting the whole file doesn't.**
- **Keep ExternalSecrets in their own file,** separate from the workloads, so a fresh cluster isn't
  held up waiting for the operator's CRDs.
